## 1. Managed memory path (cudaMallocManaged + cudaMemAdvise per byte-range)

**Design**: one `cudaMallocManaged` allocation per stacked parameter (or per layer), `cudaMemAdvise(cudaMemAdviseSetPreferredLocation, CPU)` on cold-expert byte ranges, GPU-preferred on hot ranges. Single base pointer → kernel arithmetic addressing unchanged → **b12x delta: ZERO**.

- TMA + managed: CUDA documents no UVM page-fault/migration semantics for `cp.async.bulk.tensor` and recommends prefetching managed ranges before TMA ([CUDA 13.1 programming guide, Asynchronous Data Copies](https://docs.nvidia.com/cuda/archive/13.1.0/cuda-programming-guide/04-special-topics/async-copies.html); [Unified Memory overview](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html)). **Moot here**: weights load via cp.async (SM-issued, UVM-fault-capable), and TMA is used only for activations, which are always GPU-resident (`dynamic.py:4480-4496` A/SFA partitions).
- w4a8 in-place repack: writes traverse the same pointer; with cold ranges CPU-preferred the repack would churn pages GPU↔host. Fix by ordering: repack first (all pages device-resident), then advise+`cudaMemPrefetchAsync` cold ranges to CPU. One-time cost, same class as the PCIe repack already paid for ords 20-22 (13 §4).
- Code delta: ~100-200 LOC vllm-side (allocation shim via cuda-python/`cudaMallocManaged` + tensor wrap, advise/prefetch plan per expert range, uva.py-style walk variant); no image change. torch has no per-allocation managed allocator (CUDAPluggableAllocator is process-global — unusable), so a small shim is required either way.
- Viability: **viable but second choice**. Risks: UVM migration heuristics under graph replay, fault-servicing latency on GB202 PCIe unvalidated, 2 MiB page granularity (same as VMM). Preferred only if the VMM host-location probe (§2) fails.

## 2. VMM / cuMemMap path — scout's impossibility claim PARTIALLY REFUTED

- What CUDA VMM **can** do: `cuMemCreate` with `CU_MEM_LOCATION_TYPE_HOST` (or `HOST_NUMA`) creates pinned **host** physical allocations, `cuMemAddressReserve`+`cuMemMap` maps them into a CUDA VA range, `cuMemSetAccess` grants device access — i.e. **one VA range can mix device-backed and host-backed 2 MiB pages** ([CUDA Driver API, Virtual Memory Management](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__VA.html); [VMM programming guide](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html)). Constraint found: host-located allocations cannot be IPC-exported (`CU_MEM_HANDLE_TYPE_NONE` only) — irrelevant for single-process ranks.
- What it **cannot** do (scout's claim, confirmed for that scope): existing `cudaHostAlloc`/`cudaHostRegister` memory (what today's UVA offload pins, `get_accelerator_view_from_cpu_tensor`, `<SP>/vllm/utils/torch_utils.py:915-935`) cannot be `cuMemMap`'d — only cuMemCreate'd physical handles can.
- **Design P4 (recommended)**: allocate ords 20-22's stacked params in ONE VMM VA range each; hot experts' pages device-backed, cold experts' pages HOST-backed. One pointer, one `data_ptr()` → plan/weight caches, prepared-weights contract (`_impl.py:492-514`), CUDA-graph capture (pointer static, no faults ever), and the in-place repack all work unchanged. Repack runs while all pages are device-backed; cold ranges are then remapped to host pages before serving.
- Page granularity: 2 MiB pages vs 3.75 MiB w13 slice per expert → adjacent experts share a boundary page; effective quantum ≈ expert ± 0.5 MiB (~6-8 MiB). Choose cold sets as page-aligned expert ranges; no topk_ids remap needed (slots keep their indices).
- Code delta: ~300-330 LOC, all host-side: VMM allocator + torch-tensor wrap shim (~150), placement policy (~60), uva.py-walk variant (~80), optional idle-time remap API (~40). Platform gate: probe `cuMemGetAllocationGranularity` with a HOST-location prop + a device read test on GB202/Linux before committing (20-line script).

## 3. Per-expert pointer-table kernel change (the scout's 'blocked' path — real, but moderate, and unnecessary here)

For the executed w4a8 path the change is a **new staging mode, not a rewrite** (kernels are JIT Python):
- Add 4 kernel params: device Int64 tables `w13_bank/down_bank/sfbw13_bank/sfbdown_bank[E]` (byte base per expert; null ⇒ legacy arithmetic mode, compile-time `const_expr` flag keeps today's specialization).

- Launch ABI + policy encoding (`_impl.py:11619-11723`, `_encode_dynamic_launch_policy` `:11572-11592`), prep/bank construction, and vllm wiring: ~150-200 LOC. **Total ≈ 400-500 LOC** across `dynamic.py`/`_impl.py`/`b12x.py` + vllm side.

This is why the pointer-table path is strictly worse than P4 for this placement; its value is as an **upstream b12x contribution** (also unlocks vLLM #57943's StagingBank, since b12x rejects `expert_map`, `b12x.py:790-791`).
- TMA recipes (nvfp4 / `w4a8_b_tma`): per-expert descriptors (384×4 tensors×20 layers ≈ 30k descriptors) are impractical as launch params; the sane variant is the §4 two-bank dual-descriptor form with a per-task runtime branch between two traced `cute.copy` calls (uniform per task — every tile of a task belongs to one expert).

## 4. Split-tensor / two-base design

Same indirection requirement as §3 (kernel must still choose the base per expert), so for the executed cp.async path it is a special case of §3 (two table entries or bank_base+offset arithmetic).
